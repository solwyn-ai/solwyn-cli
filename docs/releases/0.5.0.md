Solwyn CLI 0.5.0 moves to account API keys. A key belongs to your account and holds one or more projects, and every request made with it names its project. A repository names its Solwyn project in a committed `.solwyn.env` file, and there is no computer-wide default project any more. Coding agents get the project from the repo and their key from `solwyn keys env`, and the MCP reporting tools spend from the one project chosen at launch.

Covers changes since [v0.4.3](https://github.com/solwyn-ai/solwyn-cli/releases/tag/v0.4.3).

## Install or upgrade

```sh
uv tool upgrade solwyn-cli                 # new installs: uv tool install 'solwyn-cli==0.5.0'
pipx upgrade solwyn-cli
pip install --upgrade solwyn-cli
solwyn --version                           # solwyn 0.5.0
```

Requires Python 3.11 or newer and a Solwyn API that serves account API keys (`/api/v1/keys`, `GET /api/v1/auth/key` and the `Solwyn-Project` header). The production API does once it runs the WS-14 release.

## Upgrading from 0.4

0.5.0 is a breaking release. Check scripts, CI and agent configurations against this list.

1. **Project keys (`sk_proj_...`) stopped working.** The API replaced them with account API keys (`solwyn_sk_...`). The first `login`, `logout` or key command after the upgrade removes the old key from the credential store and says once: "Removed an old project key (sk_proj_...). Old keys stopped working; run solwyn keys create --store-key for each repo." Create a key per repo with `solwyn keys create --project PROJECT --store-key`, or in the dashboard under Settings > API keys.
2. **Name the project with every key.** Set `SOLWYN_PROJECT` (a project name or `proj_` id) next to `SOLWYN_API_KEY`. The CLI sends it as the `Solwyn-Project` header. A key without a project is refused with `project_selector_required` (exit 2).
3. **`SOLWYN_PROJECT_ID` and config `default_project` are gone.** The project comes from `--project`, then `SOLWYN_PROJECT`, then the repo's `.solwyn.env`. A command that needs a project exits 2 with `usage_error` when only `SOLWYN_PROJECT_ID` is set; `init` and `projects create` refuse it the same way before they create a project, store a key or write `.solwyn.env`. A `default_project` left in `config.toml` is ignored and dropped on the next config write, and `config set default_project` exits 2 (`Invalid configuration key`).
4. **`--project` accepts a name.** With a login, a name is turned into its `proj_` id through the login's projects; with an API key, through `GET /api/v1/auth/key`. URLs always carry the id. A renamed project's old name stops working; its id always works.
5. **`keys` commands changed.** `keys show` is gone. `keys rotate KEY_ID` and `keys revoke KEY_ID` take the key id as an argument (no `--key-id`, no project). New: `keys list`, `keys create`, `keys remove-project`. `keys env` emits `solwyn.keys-env.v2` and exports `SOLWYN_PROJECT` too.
6. **MCP read tools take `project`, not `project_id`.** Reporting tools take no project at all; they use the launch project.
7. **`init` writes `.solwyn.env`, not `config.toml`.** Its JSON is `solwyn.init.v2` (no `config_path`; adds `project_name`, `project_created`, `key_stored`, `repo_file`, `repo_file_written`). It no longer prompts for a project, a project name or a budget.
8. **`login --with-key` needs a project** (`--project`, `SOLWYN_PROJECT` or `.solwyn.env`) and checks the key with `GET /api/v1/auth/key` before storing it.

## Added

### Account API keys

- `solwyn keys list` lists the account's live keys with their projects and marks the ones stored on this computer (`solwyn.keys-list.v1`).
- `solwyn keys create [--project P] [--name] [--scope] [--store-key]` creates a key for exactly one project. With `--store-key` it is stored for that project and no secret is printed; otherwise it is shown once with export lines for `SOLWYN_API_KEY` and `SOLWYN_PROJECT`.
- `solwyn keys rotate KEY_ID` keeps the key's projects. When this computer stores the key, the stored copy is replaced and no secret is printed; otherwise the replacement is shown once. The replacement is never lost: if the store fails after the rotation, it is shown instead.
- `solwyn keys revoke KEY_ID` and `solwyn keys remove-project KEY_ID --project P` also delete this computer's stored copies.
- Giving a key another project is done only in the dashboard; `solwyn keys add-project` only says so (exit 2).
- `solwyn keys env` prints the stored key for the selected project as `SOLWYN_API_KEY`, `SOLWYN_PROJECT` and, off the default API, `SOLWYN_API_URL`. It never reads `SOLWYN_API_KEY`, and refuses a project other than the one `.solwyn.env` names (`project_mismatch`), a project with no stored key (`api_key_not_stored`), a stored key of another account than the login (`api_key_account_mismatch`) and, without a login, a name that keys of two accounts share (`project_ambiguous`).

### Keys stored per project

- The credential store keeps keys per (API, project id), with the key id, the owning account and the project name (file version 2; in the keychain one item per key plus a sharded index, so logout finds every key and a damaged index is reported, never read as empty).
- A stored key is chosen by its exact project id. With a login present, even under `SOLWYN_AUTH=project_key`, a project name is resolved through the login's account; a `SOLWYN_TOKEN` login reads its account from `/api/v1/accounts/me` and fails closed (`account_unresolved`, exit 3).

### The repo file and `init`

- `.solwyn.env` at the git root names the repo's project. It holds no secret and is meant to be committed:

  ```text
  # Solwyn project for this repo. Not a secret: commit this file.
  SOLWYN_PROJECT="checkout-bot"
  ```

  The CLI writes it only when it is missing and never overwrites it. `projects rename` updates it when it names the old name, and leaves it alone (saying so) when it is edited while being updated.
- `solwyn init` uses the project `.solwyn.env` names; else an existing project selected with `--project` or `SOLWYN_PROJECT` (it never creates a project from those); else it creates a project named after the repo (`-2`, `-3`, ... when taken, with `--budget`, `--period` and `--mode`), stores its key and writes `.solwyn.env`. A `--project` or `SOLWYN_PROJECT` that disagrees with `.solwyn.env` exits 2 before anything is created or written. A selected project is written to `.solwyn.env` only after init has read its budget and finished every other step, so a project that does not exist or cannot be read is never recorded.
- `solwyn projects create` defaults `--name` to the repo's name (with the same suffix rule); `--store-key` also writes `.solwyn.env` when missing.
- `init --agents` guidance tells agents that the repo's project lives in `.solwyn.env`, to hand keys to SDKs with `solwyn keys env`, and never to switch projects or ask for a wider key to get past a limit.

### MCP

- `solwyn mcp` uses one launch project: `--project` before `mcp`, else `SOLWYN_PROJECT`, else `SOLWYN_PROJECT` in the repo's `.solwyn.env` (from the server's working directory). These, the server's environment, its working directory and the credential store selection (`SOLWYN_CREDENTIAL_STORE` or config `credential_store`, and `SOLWYN_CREDENTIALS_FILE`) are read once at start, so editing them later, or a retry after a failed first call, never selects another project or key. If the stored login is replaced, removed or added before the reporting tools are bound, they refuse with `credentials_changed` until the server restarts; once bound, the chosen key is kept. It is resolved with the same rules as the CLI, including the mismatch check against `.solwyn.env` and the account check against your login.
- The reporting tools (`budget_check`, `budget_check_batch`, `budget_confirm`, `record_call`) always spend from the launch project. They take no project argument and refuse one, and use `SOLWYN_API_KEY`, else the key stored for that project; no other key is ever tried. The first reporting call checks the key and project with `GET /api/v1/auth/key`; every reporting request then carries the project id as `Solwyn-Project`, and results include `project_id` as Core reports it.
- When the launch project cannot be used (`project_mismatch`, `api_key_not_stored`, `api_key_account_mismatch`, `credentials_changed`, an expired or revoked key), every reporting call returns that error until the server restarts. Read tools keep working.
- Read tools take `project` (a name or `proj_` id) instead of `project_id`, defaulting to the launch project. This renames a tool argument; update MCP clients that pass `project_id`.
- `solwyn doctor --mcp` adds a `key_project` check: the key and launch project checked together with `GET /api/v1/auth/key`, reporting the project's name, id, budget mode and the key's expiry, or Core's refusal.

### Errors

- New error codes with messages and hints: `api_key_invalid`, `api_key_expired`, `key_not_dedicated`, `api_key_not_allowed` and `read_only_key` (exit 3); `project_selector_required`, `project_not_found`, `project_selector_conflict`, `project_ambiguous`, `project_mismatch`, `api_key_account_mismatch`, `repo_file_invalid` (exit 2); `api_key_limit_reached` (402) and `key_projects_changed` (409) (exit 1). `shared_keys_reach_project` (409) points at the dashboard; the CLI never removes keys from a project for you.
- API keys (`solwyn_sk_...`) are redacted from every output except their deliberate one-time display.

## Changed

- `whoami` names an API key credential as "API key"; help and docs say "API key" where they said "project key". The `project_key` value of `SOLWYN_AUTH` and of `auth_type` fields is unchanged.
- Removing a team member no longer revokes keys they created; keys belong to the account.
- Plan output's dashboard path is `/settings/billing`.
- `init --agents` guidance and the MCP `budget_status` description give the polling command as `solwyn --json budget status`; the old `solwyn budget status --json` never parsed. A read-only key's hint in `budget check` and `budget confirm` now names `solwyn keys rotate KEY_ID --scope full`.
- The vendored API contract is synced from Core at the WS-14 release.
