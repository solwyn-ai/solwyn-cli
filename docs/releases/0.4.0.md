Solwyn CLI 0.4.0 replaces terminal password login with a browser-approved device login. A login is a scoped CLI credential: it can read, stop agent runs and lower a budget cap on its own, and every other change waits for your approval in the browser. Coding agents get guidance that reserves guardrail changes for humans, and MCP errors now say which limit was hit. 0.4.0 is also the first release whose package description carries the MCP Registry ownership marker.

Covers changes since [v0.3.0](https://github.com/solwyn-ai/solwyn-cli/releases/tag/v0.3.0) (2026-10-14).

## Install or upgrade

```sh
uv tool upgrade solwyn-cli                 # new installs: uv tool install 'solwyn-cli==0.4.0'
pipx upgrade solwyn-cli
pip install --upgrade solwyn-cli
solwyn --version                           # solwyn 0.4.0
solwyn login                               # required once after upgrading from 0.3.0
```

Requires Python 3.11 or newer and a Solwyn API that serves scoped CLI login. The production API does. If you point `--api-url` at another deployment, it must run a Solwyn API release with the `/oauth` device endpoints, or `solwyn login` fails with not-found.

## Upgrading from 0.3.0

0.4.0 is a breaking release. It changes how you log in, which credential a command uses, and some JSON payloads. Check scripts and agent configurations against this list.

1. **Run `solwyn login` again.** Logins stored by 0.3.0 (terminal password sessions) no longer work: the Solwyn API stopped accepting sessions issued before scoped login, it refuses password login from the CLI, and 0.4.0 no longer refreshes session tokens. `solwyn login` prints a URL and a code on stderr. Open the URL, sign in, check the code and approve. The CLI never opens a browser, so this works over SSH and from an agent, which can relay the URL and code to you. Login and logout delete the old 0.3.0 keychain entries where the keychain is in use.
2. **Credentials have a new home, keyed by API URL.** macOS and Windows keep using the OS keychain. Linux (desktop, headless, WSL, containers and CI) now uses a private `0600` file, `~/.local/share/solwyn/credentials.json`, instead of the system keyring. Every stored credential is now kept per API URL. Nothing is migrated:
   - Run `solwyn login --with-key` again for a project key stored by 0.3.0 (all platforms).
   - 0.3.0 kept its login (`access_token` and `refresh_token`) and project key (`api_key`) in the system keyring. 0.4.0 never uses them. At a terminal, a command that finds no credential says once that they are there: run `solwyn login` again for the login, and `solwyn login --with-key` (or `SOLWYN_API_KEY`) for the key. `solwyn logout` deletes them.
3. **A login now wins over a stored project key.** Every command except metering uses `SOLWYN_TOKEN`, then the stored login, then `SOLWYN_API_KEY`, then the stored project key. In 0.3.0 a project key took precedence over the login. Metering (`budget check`, `budget check --batch`, `budget confirm`, `record` and the matching MCP tools) uses only a project key: `SOLWYN_API_KEY`, then the stored key, never a login. To pin the old behavior for a script, set `SOLWYN_AUTH`:
   - `SOLWYN_AUTH=project_key` skips both logins.
   - `SOLWYN_AUTH=login` requires `SOLWYN_TOKEN` or the stored login, with no fallback to a key.
   - Any other non-empty value exits `2`. An empty value counts as unset.
4. **Handle exit code `6`.** It is new. A change a login cannot make on its own (raising a cap, changing enforcement mode, pausing or snoozing rules, keys, projects, billing, channels, team changes) prints an approval URL and waits for the browser. Exit `6` means the change was not applied: the approval is pending, denied, expired, invalid or over the limit of five pending approvals. `solwyn login` also exits `6` with `login_pending` when its wait ends before you approve. Exit codes `0` to `5` keep their meanings. In unattended runs either approve within `--approval-wait` (default 90 seconds without a terminal) or re-run the command printed in the error's hint, which carries `--approval ID`.

Other breaking changes:

- **`invite accept` is retired.** It exits `2` with `invite_accept_retired`. Accept from the link in the invitation email, then run `solwyn login`. `invite show` is unchanged.
- **`account recover` is retired.** It makes no request and exits `2` with `account_recover_moved`. After you are removed from every account, create a personal account in the dashboard at https://app.solwyn.ai/no-account, then run `solwyn login`.
- **Login JSON is `solwyn.login.v2`.** `solwyn.login.v1` is gone. The new payload is flat and adds `store` and `location` (where the credential was saved), `credential_id`, `label`, `scope`, `expires_at`, `account_id`, `account_name`, `email` and `role` (all null for `--with-key`). `auth_type` is `login` or `project_key`.
- **`whoami` payload changed.** `solwyn.whoami.v1` keeps its name, but `auth_type` is `login` instead of `jwt`, and a new `credential` object names the credential in use (`kind`, `source`, `location`, `label`, `scope`, `expires_at`). `source` and `auth_source` are `keyring`, `file` or `environment`. The table output starts with a `Credential:` line and adds `Stored in`.
- **`logout` looks in both stores.** Whatever store is selected, it revokes every login it can read for this API in the credentials file and the keychain, then clears both and the 0.3.0 keyring entries, under the credential lock. `solwyn.logout.v1` gains `revoked`, `logins_found` and `stores` (each with `status`: `cleared`, `absent`, `unreachable` or `unread`, and `kept`). `cleared` is true only when nothing remains. An unreachable store, or an entry it could not read, makes logout exit `3` with `logout_incomplete`, naming what was kept; an unread login is never deleted or revoked. A failed revoke of a login it did read still clears it, exits `0` and says to revoke it in the dashboard.
- **`doctor` reports `credential_store`** instead of `keychain`, naming the store and path. `doctor --mcp`'s credential `source` can be `file`.
- **`config` gains `credential_store`** (`auto`, `keyring` or `file`).
- **Error code `jwt_required` is now `login_required`.** User-facing text says "login" instead of "JWT".
- **MCP `credential_requirement`** in tool descriptions and `doctor --mcp` output is `login` instead of `jwt`.
- **Logins expire after 30 days** and are never renewed silently. A command run with an expired login says when it expired; run `solwyn login` again.
- **An unexplained 401 is an authentication failure** (exit `3`). There is no session refresh any more. 401s for a revoked, expired or invalid CLI login carry a `Run solwyn login` hint.

## Added

### Browser login

- `solwyn login` runs the OAuth device flow (RFC 8628). Options:
  - `--scope read|read,contain` (default `read,contain`). `contain` lets the login stop agent runs and lower the primary budget cap without an approval.
  - `--label` names the login (default: the short hostname).
  - `--wait SECONDS` sets how long to wait for the browser: 600 with a terminal, else 90. `--wait 0` starts the login and returns at once.
  - `--continue` resumes a pending login after you approve it.
- When the wait ends first, the pending code stays in the credential store and the command exits `6` with `login_pending`. Its `detail` (`solwyn.login.pending.v1`) has `user_code`, `verification_uri`, `verification_uri_complete` and `expires_at`, so an agent can relay them.
- `login --with-key` stores a project key in the same credential store. Storing one in the credentials file prints a warning: it has full project access and does not expire, so CI and agents should prefer `SOLWYN_API_KEY` from a secret manager.

### Credential storage

- One credential store per user, keyed by API URL: the OS keychain on macOS and Windows (local persistence on Windows, so it does not roam with a domain profile), and `credentials.json` in the user data directory on Linux (`$XDG_DATA_HOME/solwyn/`, default `~/.local/share/solwyn/`). The directory is `0700` and the file `0600`, written atomically. A file other users can read, or another user owns, is refused with the `chmod` to run.
- Every command reads and writes exactly one store: `SOLWYN_CREDENTIAL_STORE`, else `credential_store` in config, else `auto`. A failed keychain write never falls back to the file: the command exits 3 with `credential_storage_failed`, names the keychain and why, stores nothing, and hints `Run solwyn login --store file, or set SOLWYN_CREDENTIAL_STORE=file.` A browser login that cannot be stored is revoked on the server; a pending login (`--wait 0`) and `--with-key` store nothing. `--store` only saves the mode to config (`auto` removes it) and then logs in to that store; nothing is ever copied between stores. Writes never delete; only logout does, and it clears both stores. `whoami` and `doctor` say when the credentials file still holds this API's credentials while the keychain is in use. Pending logins live in the same store. On Linux, `auto` writes never touch the keyring.
- Stored logins are one entry each (the token and its metadata together). Every read and change of stored credentials holds one per-user lock in the user state directory (`~/.local/state/solwyn/credentials.lock` on Linux), shared for reads and exclusive for changes, whatever `SOLWYN_CREDENTIALS_FILE` says, so concurrent CLI and MCP processes never interleave. A command that waits more than 10 seconds for the lock fails with a storage error. A keychain write that does not finish within 5 seconds fails the command, and the process exits still holding the lock (an MCP server exits after answering), so the unfinished write cannot land after another process moves on.
- A credentials file that is not a valid Solwyn credentials document, or holds an incomplete login, pending login or project key, is refused with an error naming it. A stored login that is not valid, in the file or the keychain, is never skipped in favor of a stored project key.
- The credentials directory must belong to you; the CLI tightens it to `0700` and refuses one another user owns. The file is opened without following symlinks and checked on the open descriptor before it is read, so it cannot be swapped between the check and the read.
- `solwyn login --store auto|keyring|file`, saved to config, or `SOLWYN_CREDENTIAL_STORE` chooses the store. `keyring` fails loudly with no fallback, refuses plaintext `keyrings.alt` backends, ignores global keyring configuration and times out after 5 seconds. `file` never touches the keyring, except that `logout` always clears both stores. `SOLWYN_CREDENTIALS_FILE` moves the file.
- The file is plaintext protected by permissions. It is exposed to backups and to tools that read files as your user, including an AI agent's file tools. A login is scoped, expires after 30 days and can be revoked. A system keyring encrypts secrets at rest and a locked one blocks retrieval, but an unlocked one serves any program running as you. Linux defaults to the file because agent hosts and headless sessions often cannot reach or unlock a keyring.
- Login, `whoami`, `logout` and every missing-credential error name the store and path used.

### Logins for CI and cloud agents

- `SOLWYN_TOKEN` carries a scoped `solwyn_cli_` login in the environment, ahead of the stored login. CI and cloud agents can read with a 30-day, revocable login instead of a full-scope project key.
- `solwyn login --label ci --scope read --no-store` runs the browser login and prints the token once on stdout (`solwyn.login.token.v1` with `--json`). Nothing is stored. The token is never logged or included anywhere else, and the metadata printed with it is redacted like any other output.

### Approvals

- Any change that needs your approval prints the URL and a summary of the change on stderr, polls every 3 seconds for up to `--approval-wait` seconds, then re-sends the identical request once with the approval attached.
- `--approval ID` (global) attaches an approval you already granted to the first change request of the run.
- When the wait ends first, the error names the exact command to re-run, in the hint and in `detail.retry_command` and `detail.retry_argv`.
- `approvals status ID [--wait]` reads an approval (`solwyn.approval.v1`).
- MCP tools never wait. They return `approval_required` with the approval URL in the hint.

### CLI logins

- `credentials list` shows your CLI logins (`solwyn.credentials.list.v1`) and marks the one in use.
- `credentials revoke ID|--current` revokes a login by ID or a unique prefix of at least 8 characters (`solwyn.credentials.revoke.v1`). `--current` also clears it from the credential store when it is the stored login. Logins minted with `--no-store` appear in the list under their label. Revoking needs no approval.

### Handing a key to the SDK

- `keys env` prints `export SOLWYN_API_KEY=...` for the stored project key (`solwyn.keys-env.v1`). It writes nothing else and never writes a file.
- `projects create` without `--store-key` prints the same export line under the one-time key panel.

### Agent guidance

- `init --agents`, `agent-context` and the generated AGENTS.md, skill and Cursor rule gain a "Changes only a human makes" section: never raise a budget cap, never switch `hard_deny` to `alert_only`, never pause or remove budget rules, never rotate or revoke keys or change billing or the plan. If one looks necessary, the agent stops and asks.
- They also say that the Solwyn MCP server meters the calls your code makes, not the coding assistant's own model usage.
- Guidance and the README describe SDK behavior instead of naming an SDK version.

### MCP Registry

- `server.json` at the repository root describes the `ai.solwyn/solwyn` Registry entry, which runs `uvx solwyn-cli --project <id> mcp --profile guardrails`.
- The README, and so the PyPI description, carries the `mcp-name: ai.solwyn/solwyn` ownership marker. The Registry listing itself is published separately.

## Changed

- **MCP errors name what happened.** MCP tools never pass the server's free-text message to the agent. Each known error code now maps to a fixed message the CLI owns, filled only from validated fields. For example, a 402 `quota_exceeded` says "Monthly request quota reached (5000/5000). Cost analytics pause until the month resets; calls and enforcement continue." instead of "The Solwyn API rejected the request." `upgrade_required` names the required tier, and `project_limit_reached` names the limit. `approval_denied` and `approval_expired` are recognized, and `approval_limit_reached` keeps its code on a 429. Tool output schemas are unchanged.
- **`init`** starts the browser login when no credential is stored. In a terminal it asks whether to log in or store a project key; without a terminal it starts the browser login instead of stopping. On an account with no projects and no terminal, it exits `2` with `project_required`, the commands to run next in the hint, and `detail.next_commands`. It never creates a project on its own.
- **`init` snippets** read provider keys from the environment, for example `Solwyn(openai.OpenAI(api_key=os.environ["OPENAI_API_KEY"]))`.
- **`notifications set --event`** checks event names locally and exits `2` on an unknown name.

## Fixed

- On a Linux desktop, an MCP server started by Codex returned `authentication_required` for every tool. Codex starts servers with a minimal environment, which drops the session bus the Linux keyring needs. Linux now stores credentials in a file that needs only `HOME`, so the server finds your login with no host configuration. `mcp-config` gains `env_vars`: the names (never values) of variables a host should forward, namely `SOLWYN_TOKEN`, `SOLWYN_API_KEY`, `SOLWYN_AUTH`, `SOLWYN_API_URL`, `SOLWYN_CREDENTIAL_STORE`, `SOLWYN_CREDENTIALS_FILE`, `XDG_DATA_HOME` and `XDG_CONFIG_HOME`, plus `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR` when the Linux keyring is selected. Copy them into Codex's `env_vars`.
- A credential stored against one API URL was sent to any other. A login or project key stored with `--api-url http://localhost:8080` was used for `https://api.solwyn.ai`. Stored credentials are now kept per API URL.

- `runs list` and the MCP tools `list_agent_runs` and `get_agent_run` failed with an invalid-response error against current Solwyn API releases, which return `first_trace_id` and `trace_url` on each run. Both fields are now accepted and included in the output.
- `costs events` and MCP `list_cost_events` failed on every non-empty page for the same reason. Cost events now carry `is_provider_fallback`, `failover_reason`, `trace_id`, `span_id`, `trace_sampled` and `trace_url`.
- A test now compares every response model the CLI parses against the Solwyn API's OpenAPI spec, so a new API field can't break a command this way again.

## Compatibility

- **Python** 3.11, 3.12 and 3.13.
- **MCP:** `mcp==2.1.1`, protocol `2026-07-28`, and tested interoperability with legacy MCP 1.28.1 clients. Unchanged from 0.3.0. The tool catalog is unchanged: 33 tools in `read`, 37 in `guardrails`.
- **CLI contract:** command paths grew from 130 to 136 and JSON output schemas from 80 to 83 (added `solwyn.login.v2`, `solwyn.login.token.v1`, `solwyn.approval.v1`, `solwyn.credentials.list.v1`, `solwyn.credentials.revoke.v1`, `solwyn.keys-env.v1`; removed `solwyn.login.v1`, `solwyn.invite.accept.v1`, `solwyn.account.recover.v1`). Exit codes grew from six to seven.

## Known limitations

- Personal-account recovery and invitation acceptance happen in the browser only.
- The external documentation site may lag this release. `solwyn <command> --help`, MCP discovery and the [command reference at this tag](https://github.com/solwyn-ai/solwyn-cli/blob/v0.4.0/docs/commands/README.md) describe 0.4.0 exactly.
- MCP runs locally over stdio only. There is no hosted MCP endpoint.

## Trust

These are unchanged except storage: no telemetry, no update checks, no prompt or response capture, and no provider keys.

- **Storage:** CLI logins and project keys are kept in the OS keychain on macOS and Windows, and in a private `0600` file on Linux (see Credential storage above). No request or approval is written anywhere.
- **Output:** CLI login tokens and device codes returned by the Solwyn API are redacted from command output (human and JSON), error messages, prompts and MCP results. In the default login flow only the short user code is printed. Some commands print a secret because that is their point: `keys env` prints the stored project key as an export line; `keys rotate` and `projects create` without `--store-key` print a newly issued project key once; `webhooks create` and `webhooks rotate` print a one-time signing secret; `login --no-store` prints the newly issued login token once (its metadata is still redacted). Raw data commands (`costs export`, `alerts export`, `attest`) return the server's data byte-for-byte.
