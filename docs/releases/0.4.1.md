Solwyn CLI 0.4.1 fixes three problems found while testing 0.4.0 against a staging API. `solwyn keys env` now exports the API URL a key belongs to, so a staging key is never sent to production by accident. Logging in no longer deletes a project key stored by 0.3. `solwyn doctor` and `solwyn config list` now show which API URL is in effect and why.

Covers changes since [v0.4.0](https://github.com/solwyn-ai/solwyn-cli/releases/tag/v0.4.0).

## Install or upgrade

```sh
uv tool upgrade solwyn-cli                 # new installs: uv tool install 'solwyn-cli==0.4.1'
pipx upgrade solwyn-cli
pip install --upgrade solwyn-cli
solwyn --version                           # solwyn 0.4.1
```

No new login is needed after upgrading from 0.4.0. Requires Python 3.11 or newer.

## Fixed

- **`keys env` exports the API URL with the key.** A project key works only against the API that issued it. 0.4.0 printed only `export SOLWYN_API_KEY=...`, so a staging key used in a shell without `SOLWYN_API_URL` went to production. When the effective API URL (from `--api-url`, `SOLWYN_API_URL` or config) is not the default `https://api.solwyn.ai`, `keys env` now also prints `export SOLWYN_API_URL=...`. On the default API the output is unchanged. With `--json`, `export` holds the same lines and a new `api_url` field holds the exported URL, or `null` on the default API. The one-time key footer of `projects create` follows the same rule.
- **Login never deletes a 0.3 credential.** 0.4.0 deleted the 0.3 keychain entries (service `solwyn-cli`: `access_token`, `refresh_token` and `api_key`) after any successful login where the keychain was in use. A 0.3 project key is not tied to an API URL and is shown only once, so this destroyed a key that could not be recovered. Now only `solwyn logout` deletes these entries. After a login, the CLI says when one is still stored: "A credential saved by Solwyn CLI 0.3 is still stored in the macOS Keychain. Run solwyn logout to clear it (this also logs you out of this API)." No other command (`whoami`, `doctor`, `keys env` or any write) deletes them.
- **Logout says when it cleared a 0.3 credential.** In `solwyn.logout.v1`, each store now has `legacy_cleared`, the 0.3 entries it found and deleted. The table shows a "Solwyn CLI 0.3 credentials" row when it cleared any.
- **`doctor` shows the API URL in effect.** Its first check is `API URL: <url> (<source>)`, where the source is `--api-url`, `SOLWYN_API_URL`, config or the default. `solwyn.doctor.v1` gains `api_url` with `url` and `source` (`flag`, `environment`, `config` or `default`).
- **`config list` shows the effective API URL.** It printed only the saved value, usually the default, even when `--api-url` or `SOLWYN_API_URL` pointed somewhere else. The `api_url` line now holds the effective URL and its source, for example `api_url=https://api.staging.example.test (from SOLWYN_API_URL)`. `config get api_url` still prints the saved value.

## Compatibility

- `solwyn.keys-env.v1` gains `api_url`. Off the default API, its `export` field holds two lines instead of one; `eval` of it still works.
- `solwyn.logout.v1` gains `legacy_cleared` on each store. `solwyn.doctor.v1` gains `api_url`.
- The `api_url` line of `config list` now ends with its source in parentheses. Scripts that read the URL from that line should use `config get api_url` for the saved value, or strip the suffix.

## Trust

Unchanged: no telemetry, no update checks, no prompt or response capture, and no provider keys. `keys env` still prints the stored project key because that is its point; it now adds the API URL, which is not a secret.
